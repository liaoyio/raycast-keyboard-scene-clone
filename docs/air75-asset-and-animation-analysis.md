## 结论

**首页的完成度来自素材准备和前端呈现共同约束。Air75 已经有独立键帽、UV 和两套烘焙外观，但没有把键码、枢轴、尺度和参考画面的使用约定一起交付。前端因此增加了位置识别、变换恢复和取景校准。**

这能解释部分适配代码，解释不了全部问题。当前首页也使用首帧状态、异步加载和视口观察；Air75 的重复状态已经收掉。相机摆动、自动扫光、过宽的交互波纹、注释组织，以及错误的尺寸验收口径，均需要由前端实现承担。

本次发现了两处与此前反馈直接相关的问题。

- **「关灯」仍有素材残留。** Air75 Base 图已经画入彩色侧灯。把动态 RGB 权重设为零，仍会显示这些颜色。原始「单帧」图也有同样的侧灯。
- **「尺寸一致」的旧判断不成立。** 旧校准对齐的是包围盒角点投影。按实际解码顶点重新投影，在相同 1265 × 400 Canvas 和当前最终相机下，Air75 比首页宽约 44px、高约 10px。原因及测量口径见第 5 节。

现有 Air75 素材足以继续实现固定机位、短距离按压和临时 RGB 反馈。它缺少的是稳定、可复现的交付约定；没有证据要求推翻整套素材，更不需要为此添加骨骼动画系统。

## 1. 研究范围与证据边界

本报告比较三个对象，避免把原作者的实现、本地首页和当前 Air75 混为一谈。

| 对象 | 本次核查内容 |
|---|---|
| Raycast 原作者方案 | Thomas Cullen 2026-08-27 的公开制作说明，通过浏览器阅读全文 |
| 本地首页 / | 当前代码、keyboard.glb、Base/RGB 贴图、静态图和浏览器画面 |
| 本地 /air-75-v3 | 当前独立组件、运行时资产，以及 Downloads/Air75_V3 中的原始交付 |

原始 Air75 目录只有一个 GLB 和四张 PNG。没有可编辑的 DCC 工程、灯光场景、完整材质节点、动画工程、音频或交付说明。本文可以确认文件保存了什么，也可以追踪前端怎样使用它们；无法还原建模人员每一次操作或原始资产的全部制作历史。

证据分为三种。

- **高置信度事实**来自当前源码、GLB 解码、PNG 元数据、文件哈希和本地浏览器观察。
- **中置信度解释**用于受光层次、视觉节奏等审美归因。它们有画面和实现依据，仍需设计验收。
- **待确认项**包括原始布光、减面历史、完整 UV 覆盖质量，以及实际 GPU 帧耗时。

本次只研究并输出文档，没有修改应用、素材或已有组件。浏览器核查覆盖两页的静止画面、相同实体键触发的反馈及 Canvas 尺寸；没有录制逐帧性能轨迹，也没有完成全部设备的视觉验收。

## 2. 首页的「优雅」具体来自哪里

### 2.1 原作者先做了大量素材准备

Cullen 的文章说明，他主要在 Blender 中准备模型与贴图，简化模型并删除相机看不到的面，为按键安排键码名称，展开 UV，再烘焙普通和亮灯两种外观。前端按输入移动键帽，以扩散遮罩混合两张图，并播放按下、松开的音频切片。他也明确提到需要反复调参。[Thomas Cullen，How the Raycast Keyboard landing page hero was made，2026-08-27](https://x.com/thomasauros/status/2092977737837244583)

这段制作说明与本地资产的结构相符，但不能照抄成「当前首页已经完美完成所有命名」。实际文件仍有 20 个非语义网格名，后文会列出。

原文使用 TSL 描述自定义着色器。本仓库使用 Three.js 的 GLSL ShaderMaterial。两者共享双图混合思路，不能把本地代码称为原作者 TSL 源码。

### 2.2 好看的明暗，大部分在浏览器加载之前已经完成

首页 Base 图能直接看到键面明暗、边缘反光、红色装饰和机身轮廓。前端把这套外观铺回网格，运行时无需重新布光。

当前两页共享的 [shaders.ts][shader] 没有法线光照、粗糙度、金属度、灯光衰减或动态阴影计算。按键下沉时，前端额外降低该键的 uDim，制造局部变暗的反馈。

这种方法的优势是外观稳定、材质计算少，也容易让不同设备看到接近的效果。限制同样明确：键帽移动后，贴图里的阴影和反射不会跟随真实光路重新计算；大角度绕看、拆解、动态换灯会暴露这一点。

在当前短距离按压和有限相机入场的范围内，这个取舍成立。用户感受到的受光质量，更多取决于烘焙图的层次和构图。

### 2.3 页面节奏也做了限制

从 [首页 Hero][home-hero]、[Air75 Hero][air-hero] 和 [全局关键帧][global-css] 可以核对到，两页目前都采用以下处理。

- 文案依次进入，透明度、模糊、轻微缩放与位移一起收敛。
- 桌面键盘舞台固定为 400px 高。
- 舞台背景使用同一张 scene-bg.webp，底部有 200px 渐变覆盖，让机身前沿融入暗背景。
- 相机从俯视位置逐渐靠近最终视角；按键交互才触发临时 RGB。

首页保留品牌标识、说明、CTA 和补充文案，Air75 的内容更少，顶部留白也不同。它们在页面中的纵向位置和叙事节奏不会仅因 Canvas 同高就一致。Air75 无导航栏是既定要求，不能为了追求首页构图而重新加入导航。

**当前首页与 Air75 都没有鼠标相机视差，也没有自动 RGB 入场。** 这些能力不能继续被写成首页独有的优势。首页相机每帧仍做阻尼计算；Air75 抵达阈值后会固定相机，但画布仍继续渲染。

从画面对照看，首页的键面明暗过渡更连续，颜色集中在少数装饰和受光边缘。Air75 的绿色、黄色装饰键和偏细的紫色键缝形成了不同的视觉重心。这部分属于产品配色、烘焙外观与参数的共同结果，置信度为中；不能只凭「更黑」或「更多面」评价资产优劣。

## 3. 模型实际有什么差别

### 3.1 要比较当前绘制的场景，不能只看文件大小

以下数值由 GLB 结构和 Draco 解码得到。顶点数指 POSITION 顶点记录，包含 UV 接缝等原因产生的重复记录；三角形数按索引数量除以 3 计算。

| 指标 | 首页当前 Hero | Air75 当前场景 |
|---|---:|---:|
| GLB 文件大小 | 666,444 字节 | 463,176 字节 |
| 当前挂载网格 / primitive | 85 / 85 | 90 / 90 |
| 当前顶点记录 | 22,807 | 97,033 |
| 当前三角形 | 36,954 | 131,634 |
| 非 static 交互网格 / 键帽组网格 | 84 | 84 |
| 静态网格 | 1 | 6 |
| 交互部分 / 键帽三角形 | 28,555 | 115,687 |
| 静态部分三角形 | 8,399 | 15,947 |

数据源为 [首页 GLB][home-glb] 与 [Air75 运行时 GLB][air-glb]，按当前组件实际挂载规则统计。

Air75 的文件更小，当前三角形却约为首页的 3.56 倍，顶点记录约为 4.25 倍。两者多出的 94,680 个三角形中，87,132 个来自交互网格与键帽部分的差值，约占 92%。如果要做几何优化，首先应检查键帽，而非只合并外壳。

这仍然不能推出 Air75 的帧率低 3.56 倍。实际成本还受屏幕覆盖面积、着色器、提交次数、抗锯齿、GPU 和指针拾取影响。本次没有测 FPS 或 GPU 时间。

首页 GLB 内有五个场景，总计 176 个网格、158,882 个三角形。默认场景是 hero，只使用其中 85 个网格。项目当前 GLTFLoader 在独立加载复核中解析了全部场景，并触发 176 次 Draco 解码。剩余场景不参与当前 JSX 绘制，但仍有下载和加载成本。首页资产也有可整理的部分。

Draco 用于压缩几何的存储与传输，压缩后仍需要解码成网格；量化设置还可能影响精度。压缩包大小无法替代几何预算。[Google Draco 官方说明](https://google.github.io/draco/)

### 3.2 原始 GLB 到网页版本没有再整理

原始 [Air75V3黑.glb][air-original] 与运行时 air75-v3.glb 逐字节相等，均为 463,176 字节，SHA-256 为：

~~~text
e650cba521919d87e92ced64cb91ab75dd5fa0a3b914aa085f257bcde02a974f
~~~

因此，从本次提供的原始文件到当前网页文件，没有发生减面、枢轴调整、语义重命名或层级整理。网页版本改变了文件名和使用方式，没有改变模型内容。

这不代表原始文件在更早阶段完全没有优化。缺少压缩前模型和 DCC 工程，无法判断。文件中的 generator=draco_decoder 也不足以还原制作历史。

### 3.3 首页的层级适合直接交互，Air75 保留了建模分组

首页 hero 场景的 85 个网格都在根层。Air75 有 103 个节点，包含 90 个网格和 13 个非网格节点，最深为五条父子关系。

~~~text
Air75 根节点
├─ Cinema_4D_编辑器（空节点）
└─ 产品组
   ├─ 旋钮组件
   ├─ 上盖
   ├─ 两条侧灯
   └─ 实例组
      ├─ 平面
      └─ air75瑞典键帽
         ├─ 82 个直接键帽网格
         └─ 子组中的 2 个键帽网格
~~~

这个层级对建模人员有组织意义。进入当前前端组件后，网格会重新创建在一个无变换的组内，祖先节点的位移、旋转和缩放必须先合并到每个网格。于是 [createMeshStates][air-scene] 需要读取 matrixWorld，再分解成 position、quaternion 和 scale。

若直接删除这些步骤，键帽和外壳会失去父组变换。Air75 还存在一条侧灯的镜像缩放 [-1,1,1]，以及平面的 [0.99,1,1] 缩放；忽略它们会改变几何结果。

不过，层级本身不强迫研发展开所有网格。保留原场景并在内部绑定交互，也是一条可行路径。当前展开方式属于实现选择。未来若素材已平铺，就可以直接读取；若保留层级，就应沿用一个明确的层级约定。没有必要同时维护多种自动猜测机制。

名为「实例组」的节点也不等于 GPU 实例化。当前文件中是 90 份独立 mesh 定义，没有 EXT_mesh_gpu_instancing。

### 3.4 键帽已经拆开，缺的是可直接使用的键码

Air75 的 84 个键帽是独立网格，这一点适合交互。问题在命名。

| 项目 | 首页 | Air75 |
|---|---|---|
| 可直接匹配键码的名称 | 64 个 | 仅 Enter |
| 其他命名示例 | keys.276、keys.319 | 1_15、1_盲点、Space_6_25 |
| 当前补偿 | 非语义名称也被加入交互集合 | 按世界位置分行、行内排序，再映射键码 |

首页剩余 20 个 keys.xxx 名称加载后会被规范化为 keysxxx，依然无法直接匹配实体键盘的 code。它们可以通过指针触发按压和波纹，声音则可能使用公共音频模块的兜底片段。因此，首页映射代码较短，也包含了未处理完整的语义缺口。

首页 84 个非 static 网格也不能直接写成 84 个独立物理键。keys.319 是与空格重叠的薄片，只有 7 个三角形，具体用途缺少说明。

Air75 的 [mapKeyCodes][air-scene] 则承担了以下工作：

1. 查找名为 air75瑞典键帽 的节点。
2. 计算每个键帽的几何中心和世界坐标。
3. 单独找出跨两行的 ISO Enter。
4. 将其余键帽按 Z 分成六行，按 X 排序。
5. 校验行长度为 15 / 15 / 14 / 14 / 15 / 10，再分配键码。

这套逻辑对当前文件有效，但依赖瑞典布局、固定朝向、组名和 0.4 的行容差。下一份 ANSI 或不同排布的素材不能直接套用。位置排序也无法识别「位置不变但功能已改」的键位。

KeyboardEvent.code 表达物理位置，键帽印字和 KeyboardEvent.key 表达的字符可能不同。Å、Ö、Ä 不能直接当作 code；Fn 等按键还可能由硬件处理，浏览器拿不到独立事件。交付时应把「模型位置」「印字」「浏览器可接收的 code」分别说明。[MDN：KeyboardEvent.code](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/code)、[MDN：Fn 等按键的事件限制](https://developer.mozilla.org/en-US/docs/Web/API/UI_Events/Keyboard_event_key_values)

### 3.5 枢轴决定前端能否直接取得交互位置

首页 84 个交互网格中，83 个的局部包围盒中心距离原点小于 0.0001。取 mesh 的世界原点，基本就能得到按键中心。

Air75 全部 84 个键帽的局部中心都偏离原点。两个例子：

| 网格 | 局部几何中心 |
|---|---|
| 典型 1U 键帽 1_15 | [0.9500, 0.3275, 0.9500] |
| Space | [5.9375, 0.3559, 0.9520] |

典型键帽的原点靠近角落，并位于底面以下。直接用世界原点触发波纹，起点会偏到键帽边角。当前 triggerPulse 因此使用「局部几何中心 → localToWorld → 世界 XZ」。

这也解释了为何代码里同时存在 rest 和 center。rest 保存网格原点的初始世界位置，负责按压后复位；center 用于确定波纹起点。它们对应不同对象，不能只因变量多就合并。

偏置原点并不妨碍刚性平移；对当前按压来说，只要初始变换和方向正确就能工作。它主要增加了中心定位的适配。若将来要转动旋钮，旋钮的轴心和旋转轴又需要独立约定。

### 3.6 「皮肤」需要区分贴图和骨骼蒙皮

两份 GLB 的 skins、animations、cameras 都为零。

- 外观由贴图与材质决定。
- glTF 的 skin 指骨骼、关节和顶点权重。
- 当前键帽只作刚性位移，无须骨骼或蒙皮。
- 相机入场与键帽按压由前端逐帧生成，无须预制动画轨道。

「没有 animation clip」不影响当前交互。接入前需要准备好独立网格、稳定键码、初始变换和按压方向。

## 4. 贴图的制作方式，怎样限制最终效果

### 4.1 两套素材都采用烘焙外观，Air75 并未缺少 UV

两份模型都有 TEXCOORD_0，UV 均在 0–1 范围内。首页几何只含 POSITION 和 TEXCOORD_0；Air75 还保留 NORMAL。当前共享 shader 不使用 NORMAL 计算受光。

两份 GLB 都没有 images、textures 或 samplers。首页没有材质定义；Air75 有 90 份内容相同的灰色默认材质，没有连接产品贴图。前端会替换这些默认材质，手动加载外部 Base/RGB 图。

也就是说，这两套 GLB 都依赖外部使用约定，无法仅凭文件本身恢复网页外观。Air75 缺少材质绑定说明，首页通过既有代码提供了这份说明。

Air75 原始 PNG 中还有直接的制作证据。四张图都保存了 keyword=octane 的 PNG iTXt 元数据。

| 字段 | Base / RGB | 单帧 / 亮灯测试 |
|---|---|---|
| 渲染器记录 | OctaneRender Studio+ 2026.2 | 相同 |
| 输出通道 | Denoised beauty | Denoised beauty |
| 相机类型 | baking | thinLens |
| 分辨率 | 2048 × 2048 | 1280 × 720 |
| 输出 | 16-bit PNG，sRGB，非线性 | 相同，另有 Alpha |
| 后期 | 关闭 | 开启 |
| 样本上限 | 均为 1500 | 单帧 1500，亮灯测试 600 |

Base/RGB 的 baking camera 使用 uvSet=1、bakingGroupId=1、padding=4，且两图设置相同。这里的 Octane UV Set 编号不能直接作为 glTF TEXCOORD_n 后缀使用；文件实际只导出了一套 UV。

Baking Camera 会把材质与受光结果写入 UV 图，包含反射等外观。它要求正确的 UV，并可通过 padding 扩展 UV 岛边缘。[OTOY：Baking Camera](https://docs.otoy.com/cinema4d/BakingCamera.html)

因此，Air75_Base.png 是带明暗的完整外观图。把它当作纯 albedo 再交给 PBR 材质受光，会让烘焙明暗与实时受光叠加。RGB.png 也包含键帽本体和文字，不能直接当作一张独立的发光遮罩。

### 4.2 两张图混合，能做什么、做不到什么

当前 [shader][shader] 的主要关系可以写成：

~~~text
输入 → 一个按键的世界位置和波纹进度
波纹 → 在世界 XZ 平面上扩散并衰减的权重
颜色 → Base + 权重 × (RGB − Base)
按压 → 再乘该键的明暗系数
~~~

这里的彩色区域已经画在 RGB 图中。波纹只决定何处显示这套亮灯外观。它不会计算新的反射，也不会让一束真实灯光照到相邻键帽。

由此产生几项限制。

- RGB 图内的色相分布基本固定。要做任意变色、逐键独立颜色，现有双图不能完整表达。
- 按压时的真实接触阴影不会更新；uDim 只能整体压暗该键。
- 视角变化后，高光仍随表面贴图移动，缺少真实的视角依赖。
- 混合权重由表面的世界 XZ、波纹中心、进度、半径和强度等参数共同计算，不计算灯光遮挡和间接反射。

当前 shader 的 lightingMix 没有限制在 0–1，首页强度默认 2，Air75 为 1.6。靠近波纹中心时，计算可能超出两张图的线性插值范围，放大两图差异。这是现有艺术调参方式，也存在高饱和边缘被放大的风险。不能将强度值理解为真实灯光功率，更不能承诺与 Octane 的亮灯图严格一致。

### 4.3 关闭动态 RGB 后，为什么还亮

[Air75 Base 原图][air-base-original] 下方的侧灯 UV 岛已经有蓝绿、青色亮块；[原始单帧图][air-still-original] 的机身两侧也能看到彩色指示灯。本地 Air75 待机画面保留了这些颜色。

这条因果链可以直接核对：

~~~text
DEFAULT_LIGHTING=0，所有 pulse 衰减完毕
→ shader 使用 Base
→ Base 中的侧灯颜色仍被显示
~~~

如果「无灯效」包括侧灯，那么这份 Base 不符合目标。需要重新烘焙全熄灯状态，或在有明确灯区遮罩时单独控制该区域。继续降低 RGB 强度不会去掉 Base 内已有的光。

绿色、黄色键帽和红色旋钮是产品配色，不能一并去色；彩色塑料与灯光需要分别验收。静态回退也应使用同一全熄灯状态，否则桌面与移动端会出现不同定义。

### 4.4 Air75 的键缝光与首页的受光范围不同

逐张查看两套 RGB atlas，可以看到首页键帽 UV 岛的彩色边缘反射较宽。Air75 的强色有较多分布在平面 UV 岛，键帽边缘彩色受光相对窄。

这会改变同一混合遮罩的观感：首页更容易形成一个键帽周边的局部亮起；Air75 更容易出现细线状键缝。前端扩大波纹半径，只能让更多区域进入 RGB 状态，无法凭空补出贴图中缺少的宽反射层次。

这一判断由贴图观察与按 A 键的本地画面对照支持，置信度为中。尚未取得独立灯组或光照 AOV，不能把差异精确归因于某一盏灯的位置、灯强或材质粗糙度。

### 4.5 亮灯参考图多了一层后期

原始「单帧」与「亮灯测试」使用同一 thinLens 相机。两图的相机参数完全相同，但后期不同。

| Octane 后期参数 | 单帧 | 亮灯测试 |
|---|---:|---:|
| Bloom Power | 1 | 15.441 |
| Glare Power | 0.1 | 3.028 |
| Glare Blur | 0.001 | 0.063892 |
| Cutoff | 0 | 1.13921 |

Base/RGB 两张 UV 图的 postProcessing.enabled=false。亮灯参考图中的光晕因此不能全部从 atlas 混合还原。当前前端也没有对应的屏幕空间后期处理。

Bloom 与 glare 属于成像后的光晕处理，可以与渲染结果一起保存，也可以单独输出。[OTOY：Post Processing](https://docs.otoy.com/cinema4d/PostProcessing.html)

如果以后要求复现这张亮灯参考图，应先补齐同机位、同后期条件的基准。当前要求明确限制入场和待机无灯效，无需因此添加整套后期系统。

### 4.6 WebP 转换有损失，但没有证据说明它造成了整体变暗

| 文件用途 | 原始 PNG | 运行时 WebP |
|---|---:|---:|
| Base，2048² | 14,294,021 字节 | 127,884 字节 |
| RGB，2048² | 14,939,724 字节 | 307,556 字节 |
| 单帧，1280 × 720 | 4,754,523 字节 | 58,420 字节 |
| 亮灯测试，1280 × 720 | 4,748,145 字节 | 90,462 字节 |

四张 WebP 均为 8-bit 有损图像，没有保留原始 Octane 元数据或 ICC。像素布局、尺寸和方向没有改变。

将源 PNG 显式转换到 sRGB 8-bit 后比较，Base/RGB 全图 RGB 通道平均绝对误差分别约为 0.64 / 0.98，量程为 0–255；主键区 ROI 的平均误差约为 0.84 / 1.17。静态图的 8-bit Alpha 与对应源图逐像素一致。高饱和灯边的误差更明显，不能据此断言完全无视觉损失。

这些结果不支持「压缩让整个键盘明显变暗」。它们也不能代表感知色差 ΔE 或所有显示器上的视觉无差别。

当前 shared texture 配置为 SRGBColorSpace，shader 包含输出色彩转换，材质 toneMapped=false。未发现仅凭源码就可判定的重复色调映射问题。后续若追查色差，应固定色彩管线和曝光后比较，不能先用亮度参数补偿。[Three.js：Color Management](https://threejs.org/manual/en/color-management.html)

原图中的 isHdr=true 是 Octane 导出标志。实际文件为非线性 sRGB、无符号 16-bit PNG，不能据此当作浮点线性 HDR 贴图使用。

### 4.7 UV 翻转与纹理分辨率应分别处理

首页外部贴图配置 flipY=false，Air75 覆写为 true。PNG 到 WebP 没有发生上下翻转，因此这个差异来自模型 UV 与外部图像的配合约定，和 JPG、PNG、WebP 扩展名无直接关系。

glTF 的纹理原点规定在左上角；Three.js 的 flipY 决定上传时是否垂直翻转。当前外部贴图未通过 GLB 材质绑定，研发需要自行配置并验收。[glTF 2.0：Images](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#images)、[Three.js：Texture.flipY](https://threejs.org/docs/pages/Texture.html#flipY)

两张 Air75 atlas 同尺寸、同布局，顶部键区平移搜索的最佳位移为零，支持两图同位配准。这不等于已经证明全模型 UV 无重叠、无拉伸或分辨率分配合理。

当前 padding=4 也只能说明导出设置。缩小后的 mipmap 是否串色，必须在目标尺寸检查。图里的黑色区域可能对应有效的黑色产品表面，不能只统计黑色像素就宣布 atlas 浪费。

## 5. 键盘尺寸为什么仍与首页不同

### 5.1 Canvas 尺寸、几何投影和肉眼轮廓是三个测量对象

本轮浏览器中，两页视口均为 1280 × 720，Canvas 的 CSS 尺寸均为 1265 × 400，内部位图均为 2213 × 700。两页画布确实同大。

最终键盘大小还取决于模型坐标、模型变换、相机位置、FOV、注视点和裁切。像素清晰度与画布位图尺寸有关，物体的 CSS 画面占比则由投影共同决定。

两份模型的实际顶点世界外接尺寸如下，单位为当前场景坐标单位。

| X / Y / Z | 首页 Hero | Air75 |
|---|---:|---:|
| 宽 X | 3.189035 | 31.889898 |
| 高 Y | 0.169714 | 2.190000 |
| 深 Z | 1.289041 | 12.874416 |

宽度约相差 10 倍，但高度与深度比例并非完全相同。仅凭数值无法认定是哪一步把厘米当成米；两套素材都没有随附可核对的实体尺寸约定。glTF 规范采用米作为线性距离单位，工程若另行归一化，应记录变换。[glTF 2.0：Coordinate System and Units](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units)

### 5.2 旧校准把包围盒的空角也算进去了

以下计算使用当前源码中的最终相机，Canvas 统一为 1265 × 400。

| 参数 | 首页 | Air75 |
|---|---|---|
| 相机终点 | [0, 3.5, 1.5] | [0, 52.032, 28] |
| 注视点 | [0, 0, 0] | [0, -0.207, 0] |
| 垂直 FOV | 20° | 12.232° |

| 投影口径 | 首页宽 × 高 | Air75 宽 × 高 |
|---|---:|---:|
| GLB accessor 包围盒八角 | 1062.06 × 372.73px | 1062.10 × 372.75px |
| 解码后真实顶点 | 1010.29 × 360.45px | 1054.30 × 370.24px |

旧的「两者约 1062 × 372.7px」已完整复现，但它测量的是包络。

首页 static 网格带有旋转。局部轴对齐包围盒会组合出几何中不存在的角点；这些空角旋转后放大了外接范围，再经透视投影放大画面范围。首页世界 Y 高度因此会从真实顶点的 0.1697，被包围盒角点估计为 0.3686。

Air75 的这类估计误差较小。用两边误差不同的包围盒作为目标，会让数值看似一致，实际几何仍偏大。

**按真实顶点投影，当前 Air75 宽度多 44.01px，约 4.36%；高度多 9.78px，约 2.71%。** 这是本轮独立复核的高置信度结果，也修正了此前尺寸已一致的判断。

真实顶点投影仍不等同于最终可见像素。它未计算遮挡、背面剔除、贴图内容及 CSS 渐变造成的轮廓淡出。正确验收应先用真实几何校准，再核对相同背景、相同渐变和相同缩放下的最终截图。

这个问题属于前端测量方法。修改贴图清晰度、增加状态变量或重命名键帽，都不能修正它。

### 5.3 相同终点大小，也不代表相同入场运动

首页相机从 [0,4.5,0] 到 [0,3.5,1.5]，俯角约从 90° 到 66.80°；Air75 从 [0,70,8] 到 [0,52.032,28]，俯角约从 83.50° 到 61.81°。

两条路径的起点、透视和最终俯角都不同。当前阻尼系数也分别为 4.5 和 4。即使终点投影对齐，入场时每个键帽的屏幕位移和速度仍会不同。

因此，相机验收需要同时看起点、过渡和终点。只复制一个 FOV，或只让结束画面同宽，不足以复制整段运动。

### 5.4 原始静态相机有记录，但不能直接复制到 Canvas

两张 Air75 静态 PNG 保存了 300mm 焦距、36mm sensorWidth、约 6.867° FOV，且 orthographic=false。它们是弱透视的长焦成图，不应被称作正交渲染。

这组 FOV 与 36mm / 300mm 的水平视场公式吻合。Three.js 的 PerspectiveCamera.fov 使用垂直角度，还要结合画幅比例转换。[Three.js：PerspectiveCamera](https://threejs.org/docs/pages/PerspectiveCamera.html)

PNG 记录的相机位置、目标点与当前 GLB 坐标还缺少可核对的转换关系。GLB 中名为 Cinema_4D_编辑器 的对象只是空节点，cameras 数组仍为空。素材含有部分相机信息，但没有提供一台可直接用于当前网页坐标系的相机。

按 8-bit 解码测量，两张静态图的 Alpha>0 包围盒均为 1066 × 359，位于 1280 × 720 的画幅内；若直接使用源 PNG 的 16-bit Alpha，极弱边缘会使宽度增至 1067。它们适合彼此切换；与当前 Canvas 的匹配仍需另行校准。首页静态图还包含底部暗色渐隐，Air75 原始静态图则保留完整机身轮廓，两者的图片边界没有相同视觉含义。

## 6. 前端哪些步骤有必要，哪些是自己增加的

### 6.1 KeyboardModel 上的回调没有负责动画计算

~~~tsx
<KeyboardModel
  active={sceneActive}
  onFirstFrame={() => setRenderReady(true)}
/>
~~~

active 控制交互与场景启用，onFirstFrame 通知外层资源已进入首个帧循环。实际相机运动由 CameraRig 的 useFrame 计算；键帽位移和波纹进度由 KeyboardModel 的 useFrame 更新。

首页 [Scene][home-scene] 也有同样的首帧回调、renderReady 和 sceneActive。当前 Air75 的外层 Hero 已没有 sceneReady、sceneFailed、两个 setter 回调和断点 reset effect，首帧状态集中在 Scene，外层通过 aria-busy 的 CSS 条件控制显示。

这类状态每次挂载只完成一次准备通知。相比之下，键帽和波纹的高频变化直接更新 Three 对象与 uniform，没有逐帧调用 React setState。分析性能时，需要把两者分开。

这里还要修正「首帧」的叫法：useFrame 在渲染之前运行。当前回调可以确认资源已挂载并进入帧循环，不能单独证明 GPU 完成绘制或像素已经呈现。[R3F：useFrame 官方文档](https://raw.githubusercontent.com/pmndrs/react-three-fiber/master/docs/API/hooks.mdx)

### 6.2 生命周期保护与素材质量无关

当前两套组件都需要应对资源异步加载、离屏、卸载和错误回退。Air75 在未就绪时强制允许初始帧，再按 active 切换帧循环；CameraRig 放在 Suspense 外，先建立相机姿态。

初始 always 让启动时机明确可控，但它并非产生首帧的唯一办法。R3F 在网格挂载和属性变化时会安排新帧，demand 也能启动。若取消全部 ready 门控，位于 Suspense 外的相机可能在模型加载期间就开始运动，等模型出现时，入场已经走过一段。输入释放、错误边界和资源清理也各有职责，修好 GLB 键名不会消除它们。

可以讨论是否需要外层延迟显隐、是否接受先显示空画布，以及怎样用更少状态表达它们。但这属于页面生命周期设计，应按展示目标取舍，不能以「素材补全后都能删掉」作承诺。

### 6.3 适配发生在准备阶段，持续成本在绘制阶段

[mapKeyCodes][air-scene] 的分行排序、包围盒计算和 createMeshStates 的矩阵分解在 useMemo 准备阶段执行。数据依赖变化或重挂载会重做，正常逐帧动画不会反复排序。

当前持续工作主要包括：

- 10 个波纹槽位的进度检查。
- 按键集合检查、被按键帽的阻尼位移和 uDim 更新。
- 网格绘制、每片元双图采样和波纹距离计算。
- 指针交互时的命中检测。

两套场景都创建 84 个独立交互材质，再加一个共享静态材质，总计 85 个自建材质实例。共享静态材质不会自动合并网格提交。全部网格可见且提交、没有额外 pass 时，可推导约 85 / 90 次绘制；这不等于实测 draw calls，也不等于 85 / 90 个不同 shader 程序。

Air75 相机收敛后停算，画布在 ready 且 active 时仍为 always。Observer 上下还各保留 120px 观察余量，刚离开视口的舞台未必立即停用；进入 demand 后，尺寸或属性变化也可以触发新帧。静止不动不代表 GPU 停止工作。若以后优化空闲耗电，需要让入场、按压、回弹和波纹衰减共同管理唤醒与停止，不能只把 always 改成 demand。直接修改 Three 对象时，按需渲染需要显式安排新帧。[R3F：Scaling performance](https://raw.githubusercontent.com/pmndrs/react-three-fiber/master/docs/advanced/scaling-performance.mdx)

### 6.4 Air75 的宽波纹不能全部归因于模型大十倍

| 参数 | 首页默认值 | Air75 当前值 | 按模型宽度约十倍归一后的差别 |
|---|---:|---:|---|
| 按压深度 | 0.025 | 0.22 | Air75 约为首页的 0.88 倍 |
| 波纹半径 | 0.15 | 9 | Air75 约为首页的 6 倍 |
| 羽化宽度 | 0.08 | 1.5 | Air75 约为首页的 1.875 倍 |
| 波纹时长 | 0.9 | 1.6 | Air75 衰减更久 |
| easing strength | 3 | 1.5 | 衰减与扩散曲线不同 |
| RGB 强度 | 2 | 1.6 | 独立的视觉调参 |

首页参数可被 Dialkit 改动，表中采用 [constants.ts][constants] 与 [scene-config.ts][scene-config] 的默认值；Air75 使用当前文件内常量。

因此，Air75 同一次按键影响更多邻键，包含了主动放大的视觉参数。资产尺度只解释所需的单位换算。

两套还都把单帧 delta 限制为最多 1/30 秒，波纹使用累计后的帧时间推进。低帧率时，动画实际墙钟时长可能延长。当前未测到因此造成的卡顿，不能把它当作已经发生的性能故障；它属于后续低性能设备测试应覆盖的前端时序行为。

### 6.5 文件压小，不等于显存明显变少

两套 Base/RGB 都是两张 2048² 贴图。按普通 RGBA8 纹理及完整 mipmap 估算，合计约 42.7MiB，尚未计入解码副本、几何、帧缓冲和抗锯齿。这个数值是容量估算，本次未直接测显存。

WebP 减少了下载体积，解码上传后的容量主要仍取决于尺寸和 GPU 存储格式。降低图片文件字节与降低纹理驻留量是两项不同工作。[Three.js：Textures，Memory Usage](https://threejs.org/manual/en/textures.html)

若后续实测显示纹理是瓶颈，再比较降分辨率、重新分配 UV 或 GPU 压缩纹理。当前没有理由先加入一套复杂资源管线。

## 7. 从建模到交付，问题在哪一环出现

以下表格将已证实的文件状态与建议的制作步骤分开。它描述可追踪的制作链条，不冒充渲染同学实际操作日志。

| 环节 | 当前证据 | 给前端带来的后果 | 下一次交付应确认 |
|---|---|---|---|
| 产品结构与拆件 | Air75 已有 84 个独立键帽 | 可以直接做刚性按压，无须重建模型 | 保留键帽、静态壳体、旋钮的角色 |
| 网页几何整理 | 键帽占 115,687 个三角形；源与运行时 GLB 相同 | 当前几何处理量较高 | 在完整入场和按压范围内检查减面与不可见面 |
| 命名与布局 | 只有 Enter 直接对应 code | 研发分行排序、处理跨行键、维护布局表 | 提供稳定键码，说明 ISO / ANSI 与印字 |
| 枢轴和轴向 | 全部键帽原点偏离中心 | 研发计算几何中心，转换波纹坐标 | 统一交互原点，记录按压方向 |
| 层级和单位 | 有父组变换、镜像缩放，数值宽约为首页十倍 | 研发恢复世界变换、调相机与距离参数 | 明确层级使用方式、单位与外接尺寸 |
| UV | 有单套 UV，atlas 可正常用于当前网页 | 不需要研发重新展开 UV | 同一 UV 版本、方向、边距与可读字清晰度 |
| 材质与布光 | Octane Denoised beauty 烘焙，缺完整源场景 | 网页能复用外观，无法准确重算布光 | 保留可编辑工程；交付明确的全熄灯与亮灯状态 |
| 静态输出 | 两张图同相机，后期强度不同 | 参考图与动态材质不具同一复现条件 | 提供机位、画幅、后期和背景条件 |
| 前端交互 | 复用公共输入、shader 和声音 | 输入行为可共用，产品声音未经独立校准 | 若要求真实音色，另录 Air75 音频 |
| 验收 | 旧尺寸使用包围盒角点 | 数值匹配仍存在真实投影差 | 使用实际几何与最终画面双重核对 |

网页副本应先稳定拓扑、UV 和键码，再烘焙两种灯态。两次烘焙保持键位、UV、曝光与色彩输出不变，只改变约定的灯态；静态基准再用同一副本和指定相机生成。这样，研发拿到的模型、贴图和参考图才对应同一个版本。

模型整理应覆盖动画会看到的全部表面。只按结束画面删除背面，可能在俯视入场或键帽下沉后暴露缺口。建模人员也不应直接在唯一高精度产品模型上删面；保留母版，再导出网页用途的副本。

两份 GLB 均未提供骨骼，这对当前任务没有影响。Air75 保留的法线也不能单独增加当前网页的反射质量，因为 shader 没有使用它。若确定继续采用纯烘焙方案，可以在交付优化时评估删除未使用属性；若后续需要 PBR，则应保留相应母版和材质数据。

## 8. 最小可用交付应包含什么

不需要先建设通用资产平台。一份可复现的模型、两套语义明确的贴图和一页使用说明，已经能消掉当前多数猜测。

### 8.1 建模与渲染交付

| 交付项 | 最小要求 | 优势 | 限制或风险 |
|---|---|---|---|
| 网页模型 | 独立键帽、稳定键码；静态部件可识别 | 删除位置猜键逻辑 | 仍需核对浏览器收不到事件的特殊键 |
| 变换约定 | 明确单位、外接尺寸、按压轴和原点；选择平铺或保留层级 | 减少世界变换与中心适配 | 改枢轴时须保持几何世界位置不变 |
| 全熄灯外观 | 主键区和侧灯全部按验收定义关闭 | 默认权重为零即可满足待机要求 | 不应误改彩色塑料和装饰键 |
| 亮灯外观 | 与全熄灯图使用相同模型、UV、色彩输出和曝光条件 | 可以稳定混合 | 只支持预烘焙外观范围 |
| 参考相机 | 起点与终点、坐标转换、画幅比例和 FOV 类型 | 可复现取景 | 光凭焦距数值无法恢复网页相机 |
| 静态回退 | 按目标网页机位与全熄灯状态输出 | 减少加载/降级时的跳变 | 仍需适配响应式裁切 |
| 制作记录 | 保留 DCC 母版与版本；列出烘焙、后期及压缩设置 | 后续能重烘焙和追查差异 | 源工程可内部保存，无须全部发送给浏览器 |

单一键盘可以优先用节点名称表达 code，前端通过名称查找即可。如果必须保留建模命名，也可约定 glTF extras 中的 code 字段。选定一种即可，无须同时维护多套绑定表。

说明中应列出纹理的用途、色彩空间、UV 通道与翻转规则。将基础颜色、发光图和 beauty bake 都叫「Base」会使研发采用错误的材质路径。

### 8.2 前端接入与验收

研发应先在无动画、无交互、无舞台遮罩的状态下核对模型和贴图，再逐项加入最终取景、入场、按压与 RGB。这样能判断差异从哪一步开始出现。最终验收仍必须恢复真实页面的遮罩和布局。

验收至少覆盖以下情形。

1. 选定同一个 Canvas 尺寸，核对真实顶点投影与最终可见轮廓，分别记录宽、高和中心。
2. 检查入场起点、中段、终点，确认没有缺面、裁切或不预期的透视跳变。
3. 入场和静止时，检查主键区、侧灯；交互结束后再次检查。
4. 逐键核对实体输入和指针输入，特别是 ISO Enter、IntlBackslash、修饰键、方向键及 Fn。
5. 按住、拖过、多键同时按下、移出窗口和切换标签，确认回弹与输入释放。
6. 检查移动端、减少动画偏好、资源失败回退，以及冷加载和热加载。
7. 在目标设备测实际 draw calls、帧时间、空闲渲染和内存，再决定是否继续优化。

这些是后续验收要求，本轮没有把未执行项目记作通过。

### 8.3 当前应先处理的顺序

| 顺序 | 工作 | 所属原因 | 预期收益 |
|---|---|---|---|
| 先处理 | 按实际几何与画面重校准 Air75 取景 | 前端测量 | 解决当前仍偏大的问题 |
| 先处理 | 确认侧灯是否包含在全熄灯要求中，并产出相符的 Base/静态图 | 素材状态定义 | 消除权重为零仍有彩色灯的残留 |
| 接着处理 | 收敛入场路径与归一化后的波纹范围 | 前端视觉参数 | 缩小与首页节奏、反馈面积的差异 |
| 下次素材修订 | 补键码、整理原点与变换说明 | 交付约定 | 删除分行识别与部分几何适配 |
| 性能实测后 | 优化键帽几何、未使用场景/属性、纹理或空闲渲染 | 性能预算 | 针对实测瓶颈减少成本 |

前三项不要求重建整个模型。几何优化和交付整理可以单独进行，但每次改版都要重新核对 UV、键码和相机。

## 9. 是否需要换成完整 PBR 方案

| 方案 | 适用需求 | 优势 | 劣势与风险 |
|---|---|---|---|
| 保留双 beauty 烘焙 | 固定最终机位、有限入场、短按压、预设 RGB | 复用现有资产和 shader，改动最少 | 反射、阴影和色相变化受烘焙限制 |
| 烘焙底图加独立灯区数据 | 希望单独关闭侧灯、控制部分灯区 | 状态定义更清楚，可增加局部控制 | 需要重新制作遮罩或灯光分量；beauty 图相减不能保证物理正确 |
| 完整 PBR 与实时灯光 | 自由旋转、换材质、动态布光、拆解 | 更能表达视角与材质变化 | 需要重做材质交付、环境光、阴影与后期，并重新承担性能和视觉匹配成本 |

**当前建议继续使用双烘焙方案，先补全交付约定并修正前端校准。** 当前需求没有自由旋转和动态换材质，完整 PBR 会增加新的工作，也不能自动解决键码、尺寸测量和页面状态组织。

首页已经证明双图方案能承载这类交互。Air75 的改进重点应具体到「哪张图里的哪一类光」「哪个网格的哪个原点」「哪个参数对应哪段运动」，避免再用整体亮度、统一缩放或更多状态变量掩盖差异。

## 10. 复核方法与尚未确认的事项

### 已完成的复核

- 对三份 GLB 做结构解析、哈希比较和 Draco 解码，按默认场景及当前组件挂载范围分别统计。
- 使用项目现有 GLTFLoader 独立加载，核对节点类型、名称变化、全部场景加载与解码次数。
- 将解码 POSITION 顶点乘完整世界矩阵，再乘相机投影矩阵，计算 NDC 到 CSS 像素的外接范围；另算局部 AABB 八角，复现旧尺寸口径。
- 读取四张 PNG 的 Octane iTXt 元数据，检查相机、烘焙通道、色彩输出和后期字段。
- 查看原图与运行时图，统一到显式 sRGB 后比较像素、Alpha 和布局，避免分析工具的中间色域制造伪色差。
- 在本地两页核对 Canvas 尺寸、待机侧灯和同一实体按键的反馈。截图仅用于定性画面对照，未用于估算 FPS。

原始 PNG 的制作参数可以用项目已有 sharp 读取，无须打开渲染器：

~~~bash
node --input-type=module <<'NODE'
import sharp from 'sharp';

const files = ['Base', 'RGB', '单帧', '亮灯测试'];
for (const name of files) {
  const path = '/Users/liaoyi/Downloads/Air75_V3/Air75V3_' + name + '.png';
  const m = await sharp(path).metadata();
  const o = JSON.parse(m.comments.find(x => x.keyword === 'octane').text);
  console.log(name, {
    size: [m.width, m.height],
    depth: m.depth,
    pass: o.renderPasses,
    camera: o.renderTarget.camera,
    post: o.renderTarget.postProcessing,
  });
}
NODE
~~~

正式复测时应记录资产哈希、相机、Canvas CSS 尺寸、DPR 和动画状态，避免不同版本的数字混用。

### 仍需渲染或研发补充的证据

| 未确认项 | 当前不能下的结论 | 补充什么可以确认 |
|---|---|---|
| 原始建模拓扑、修改器、减面历史 | 「建模时完全没优化」 | DCC 工程和网页导出前后版本 |
| 灯位、灯尺寸、强度与完整材质节点 | 「某一盏灯导致键缝不好看」 | 原场景、分灯 AOV 或受控重渲染 |
| 全模型 UV 重叠、拉伸和像素密度 | 「atlas 空间利用率不合格」 | UV 检查和目标尺寸采样 |
| 精确静态相机到 GLB 的坐标转换 | 「把 PNG 的 FOV 复制即可一致」 | 导出相机及场景变换说明 |
| 最终像素轮廓完全对齐 | 「真实顶点外接框一致就验收通过」 | 同条件截图及遮罩后的轮廓比较 |
| 实际性能瓶颈 | 「三角形多三倍，所以帧率差三倍」 | 目标设备 GPU/CPU 帧耗时、draw calls 与内存测量 |

本轮已完成关键事实的交叉验证。原工程和性能测量缺口应由下一次素材交付与受控测试补齐。文档已检查链接、表格结构与代码示例，未进行独立版式渲染。
